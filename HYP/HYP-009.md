# HYP-009 — the tuner optimises a quantity that is floored, and it starts every search on that floor

**Status:** proposed
**Date:** 2026-08-29  **Pod:** (all — `lib/tune.js`, the objective function)
**Filed by:** Builder, at Fizz's request. Related: HYP-006 (the acceptance bar). See "one HYP or two" below.

## Claim

`lib/tune.js:27`:

```js
function score(m) {
  if (m.trades === 0) return -100;
  const thin = m.trades < m.days * 0.3 ? -5 : 0;
  return m.netPct - 0.5 * m.maxDDPct + thin;
}
```

`netPct` cannot go below −100 and `maxDDPct` cannot exceed 100, so **`score()` is
bounded below at −150**. Every strategy that loses substantially everything —
which is where six of seven pods sit at `DEFAULTS` — is compressed into roughly
a ten-point band at the bottom of an otherwise unbounded scale.

## What is NOT claimed, because it was measured and is false

The stronger version of this — that the objective's dynamic range across
meaningfully different strategies is about one point in a hundred and fifty — is
**wrong**, and the six HYP-002 tune runs already disprove it. Realised
`best train − base train` across 200-iteration searches:

```
pod        base train    best train      span
moon           -40.36         29.72      70.1
surge         -123.51        232.31     355.8
gapgo         -139.59        296.97     436.6
reclaim       -139.63       1052.31    1191.9
flag          -142.08        549.73     691.8
igniter       -142.11        683.26     825.4
redgreen       -97.28        255.24     352.5
```

The objective has enormous range **upward**. `netPct` is unbounded above, so once
a candidate escapes ruin the score separates candidates freely. The compression
is one-sided.

## The real claim, which is narrower and worse

**The floor is exactly where every search begins.** Four of seven pods start at
base train between −139 and −142, inside the ~10-point compressed band. In that
band, genuinely different bad strategies are nearly indistinguishable to the
objective, so the early search has almost no gradient to follow and moves close
to at random until it stumbles somewhere better.

Two observations consistent with that, from the same runs:

- **The pods starting deepest in the band show the largest spans** (reclaim,
  base −139.63, span 1192) and the one pod starting well clear of it shows the
  smallest (moon, base −40.36, span 70). From the floor, almost any escape looks
  enormous.
- **moon is also the only pod whose holdout got worse** (−6.78 → −8.09) — the
  one pod whose search had a usable gradient from the start is the one whose
  improvement did not generalise.

## This may be one HYP with HYP-006, not two

HYP-006 found the acceptance bar screens nothing: acceptance is N/N in all six
arms because the frozen validate bar is set from a champion scoring −44 and −94.

**These are the same fact seen twice.** The bar is the incumbent's score, the
incumbent is on the floor, and everything clears a floor. Fixing the objective's
floor-compression would raise the bar off the floor automatically; fixing the
bar without fixing the objective leaves it anchored to a compressed quantity.
Red Team should rule on whether they are one change or two — this file exists so
the objective half is on the record either way.

## Also contaminated, per today's four-column run

`score()` is built on `netPct`, the compounding dollar quantity. Measured across
seven pods and two arms, dollar PF and qty-weighted risk-normalised PF disagree
by more than the merge gate's own 0.03 threshold in **11 of 14 cells** (seven of
seven post-cap, four of seven pre-cap — this file previously said "five of seven
pods", which was wrong), and the disagreement is **largest on the least-ruined
pod** (moon, 0.13), not confined to ruined ones. Whatever conclusion is reached about the gate metric applies here
with more force: the gate reports a number, the objective *is optimised against*
one.

## Falsifier

1. **Not floor-bound in practice:** sample the objective over random parameter
   draws for a pod at `DEFAULTS`. If the interquartile range of `score()` across
   those draws is materially wider than ~10 points, the search is not starting
   blind and this is a non-issue.
2. **Rank-equivalent:** if replacing `score()` with a risk-normalised objective
   leaves the accepted champion unchanged across both seeds on all seven pods,
   the objective was not what was limiting the search.

## Cost

None to trading. This is search mechanics. It is a change to `lib/tune.js`, which
builders do not edit — so this file is a proposal for the owner of that file, not
work in progress.

## Result — falsifier #1 run, 2026-08-29

`research/score-range` (`c546bc5`), 168 tests pass at `50c1a6c`. `score()` and
`splitDays()` imported from `lib/tune.js`; the referee is not edited. All draws
scored on the TRAIN split (86 of 144 days), which is the split the search
compares candidates on.

**The falsifier as written is ambiguous, and the two readings disagree.** It
says "sample the objective over random parameter draws for a pod at `DEFAULTS`"
without saying whether the draws are uniform over `RANGES` or local to
`DEFAULTS`. Both were run. Reporting both, because picking the one with the
cleaner verdict would be choosing the answer.

- **Uniform reading: the falsifier fires.** Every pod's IQR exceeds ~10, the
  smallest being flag at 17.19. Range is 55–265 points and all 350 candidates
  scored distinctly.
- **Local reading: it does not fire for four of seven.** surge, reclaim, flag
  and igniter sit at 3.56–9.02, at or under the threshold.

**The local reading is the operative one.** `lib/tune.js` iteration 1 perturbs
the champion; it never draws uniformly from `RANGES`. So the cloud the search
actually starts in is the right-hand column.

### The claim survives, narrowed, and the shape is the evidence

Read together the two local columns are the signature this file predicted: for
the four pods starting between −123 and −142, **the IQR is 3.6–9.0 while the
range is 40.7–102.8.** A tight cluster just above the floor with a long thin
upward tail — most draws squashed into the compressed band, a few escaping. That
is floor compression, measured, in exactly the pods claimed.

Two supporting counts from the same clouds:

- **moon and redgreen, the two pods starting clear of the band** (−40.35,
  −97.28), have local IQRs of 45.26 and 58.12 — five to sixteen times the
  compressed pods'. The split is by starting position, as claimed.
- At temp 1.0, 21–34 of 40 draws beat the champion on the four compressed pods.
  From the floor almost anything is an improvement, which is the same fact.

### What this kills

The **"one point in a hundred and fifty"** version — already disclaimed above —
is now measured dead rather than argued dead, on both clouds.

And the **cliff branches never fire**: across 910 draws, **zero** candidates hit
`trades === 0` (−100) or the thin penalty (−5). Whatever limits this search, it
is not those two lines.

### Verdict on falsifier #1

**SURVIVES, narrowed.** The objective is floor-compressed in the neighbourhood
each search starts in, for the four pods that start between −123 and −142. It is
not floor-compressed globally, not floor-compressed for moon or redgreen, and
not blind. The falsifier should be rewritten to name the cloud before it is used
again.

Falsifier #2 (rank-equivalence under a risk-normalised objective) is **not run
and should not be**: the compounding premise behind risk-normalising `score()`
was refuted separately on 2026-08-29 (dollar/R-PF gap is *anti*-correlated with
ruin, rho = +0.74 with `netPct`), so there is no longer a motivated alternative
objective to test rank-equivalence against.
